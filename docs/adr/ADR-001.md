# MRPII Multi-Agent System — Architecture Decisions 

## 1. Project Goal

Build a decentralized MRPII system with six specialized agents that own their responsibilities, communicate through events, and negotiate to resolve conflicting requirements.

## 2. The Six Agents

| Agent | Primary responsibility |
|---|---|
| Sales | Customer inquiries, delivery options, confirmations and cancellations |
| Planning | MPS, BOM, MRP, production requirements and scheduling |
| Inventory | Stock records, availability and reservations |
| Purchasing | Procurement and supplier coordination |
| Warehouse | Receiving, storage and material movement |
| HR | Workforce availability, skills and shifts |

Each agent must have clearly defined responsibilities, tools, API endpoints, data ownership and decision boundaries.

## 3. Communication Architecture

The agreed design direction combines **A2A communication, Publish–Subscribe events, and private negotiations**.

| Mechanism | Purpose 
|---|---|
| A2A | Direct communication between agents to request information, exchange proposals or negotiate |
| Publish–Subscribe | Announce important changes to relevant subscribers |
| Private negotiation | Keep detailed proposal/counteroffer exchanges between relevant participants |
| Outcome events | Inform relevant agents about important results or commitments |

### Expected event flow

1. An agent changes something important and publishes an event.
2. The shared event system (Message Broker) delivers it to agents subscribed to that event type.
3. Relevant agents independently assess the change.
4. They initiate A2A conversations or negotiations when needed.
5. Important outcomes are published to relevant subscribers.
6. Each agent updates only the records and responsibilities it owns.

**Example:** Purchasing announces a five-day supplier delay. Planning checks production impact, Inventory checks available stock, and Warehouse checks receiving constraints if relevant. These agents may negotiate through separate A2A conversations. Planning uses the resulting commitments to reassess the schedule.

Events do not automatically trigger negotiations in every subscriber. Each agent follows its own rules.

### Decentralization principle

- Planning owns production planning; it must not become the mandatory messenger for every interaction.
- Agents can communicate directly when their responsibilities require it.
- Not every agent needs a direct connection to every other agent.
- Pub/Sub subscriptions determine which agents receive which events.
- A shared message system (Message Broker) distributes information; it does not make business decisions.

The precise level of decentralization depends on the final decision-making and coordination rules, not merely the use of Pub/Sub.

## 4. Negotiation Design

Negotiations should support proposals, counteroffers, acceptance, rejection and failure/timeout handling.

### Request prioritization

Proposed direction: each agent manages a priority queue for incoming negotiation requests.

Priority should depend on the request's urgency and impact—not simply on which agent sent it.

Possible factors:
- Deadline and urgency
- Production impact
- Customer commitment risk
- Waiting time

Safeguards:
- Prevent low-priority requests from waiting indefinitely.
- Validate priority rather than blindly trusting the sender.
- Allow independent negotiations to run in parallel.
- Protect shared resources against conflicting commitments.

**Example:** Two negotiations request the same 100 units of stock. Inventory must prevent both from reserving the same units.

## 5. Database Ownership and Consistency

Each agent owns its domain records. Other agents may read authorized information but must not directly modify another agent's records.

Examples:
- Inventory owns stock and reservation records.
- Purchasing owns procurement records.
- Planning owns its production planning records.
- HR owns workforce records.

Important changes must be communicated through events or appropriate A2A messages. Database changes alone do not guarantee that dependent agents will learn about them.

Cancellation workflow:
1. Sales reports the cancellation.
2. Planning reassesses affected plans.
3. Inventory checks and releases eligible reservations.
4. Purchasing checks whether supplier commitments can be changed.
5. Relevant agents publish updated outcomes.

Design reliable event delivery, retries, duplicate handling, and recovery from partial failures. Consider transactional event publishing (such as an outbox pattern) if needed.

## 6. Sales Agent — Current Scope (Done by my friend)

Develop Sales first and define its contact point with Planning. Do not implement the other agents merely to complete the integration.

Sales should:
- Collect customer requirements.
- Send feasibility requests to Planning.
- Present feasible options.
- Record explicit customer confirmation before creating an order.
- Report cancellations and relevant customer changes.

Planning remains external to Sales during initial development; integration will follow agreed API contracts.

### Sales database

The existing design contains nine tables:

`customers`, `products`, `conversations`, `messages`, `inquiries`, `options`, `orders`, `customer_memory`, `audit_log`.

Important distinctions:
- Conversation = overall chat.
- Message = one individual communication.
- Inquiry = one specific order request.
- Option = one proposed solution.
- Order = confirmed customer commitment.

The existing schema uses a separate `SalesAgentBase` and the `sales_agent` database schema. Preserve this isolation and verify that reset scripts do not accidentally delete Sales Agent data.

## 8. Model and Resource Usage

Initial direction:
- Six logical agents.
- One shared Qwen 3.5B model runtime through Ollama.
- No separate model copy per agent unless measurements justify it.
- Let the OS and runtime manage normal CPU/GPU scheduling.
- Measure concurrency and latency before implementing a custom AI request queue.

Keep negotiation priority queues separate from any AI inference request queue. They solve different problems.

## 9. Testing and Code Quality

The existing test suite reportedly contains approximately 140 tests. The proposed target is around 15–20 strict, high-value tests.

First review the existing tests, then merge overlapping cases and remove redundant tests. Do not sacrifice critical business-rule, edge-case, or failure coverage just to reach the target number.

Code should use meaningful names, small functions, clear responsibilities, and understandable error handling. Explain changes and test them incrementally.

## 10. Pending Decisions — Do Not Assume Finalized

Before implementing shared communication infrastructure, review and agree on:

1. **Communication technology:** Which broker or event mechanism to use.
2. **Event catalogue:** Event names, payloads, publishers and subscribers.
3. **A2A protocol:** Request/response format, correlation IDs and negotiation lifecycle.
4. **Negotiation rules:** Acceptance, counteroffers, rejection, timeouts and conflict resolution.
5. **Visibility:** Which negotiation details remain private and which outcomes are published.
6. **Priority rules:** Scoring, starvation prevention, concurrency and resource conflicts.
7. **Reliability:** Retries, duplicate events, message ordering, unavailable agents and recovery.
8. **Consistency:** Safe stock reservations and production-plan updates.
9. **Scaling:** Whether additional agent workers or AI request scheduling are necessary.
10. **Integration contracts:** Final APIs and data formats between agents.
